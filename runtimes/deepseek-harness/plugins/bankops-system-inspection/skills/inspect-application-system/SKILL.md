# 应用系统巡检

## 目标

以 `service_id` 为唯一巡检入口，先确定系统真实资产范围，再查询各对象的告警、性能与容量数据。所有判断必须能够回溯到 MCP 返回的事实；监控缺失不是“健康”。

## 输入与默认范围

- 获取 `service_id`；缺失时要求用户提供，禁止用系统中文名猜测标识。
- 默认巡检 `production`，告警窗口为最近 7 天，指标窗口为最近 24 小时；用户指定窗口时以用户要求为准。
- 在报告中写明实际环境、时间窗口和资产范围。

## 能力边界

- CMDB MCP：应用系统资产、IP、组件关系和直接外部依赖，是巡检范围的权威来源。
- AlertInfo MCP：告警、日志异常和历史生产事件。
- PerfInfo MCP：指标发现、性能与容量汇总和原始采样。
- Knowledge MCP：巡检标准、运行手册和历史经验；不能代替实时资产与监控事实。

只使用当前已加载且模型可见的工具。根据工具描述和输入 Schema 自主选择具体方法，不在 Skill 中写死工具调用序列或假设未加载的方法存在。优先使用最少充分调用，并复用已经取得的有效结果。

## 调查策略

1. 使用 CMDB 能力盘点应用与模块、Deployment/实例、带 IP 的计算节点、数据库、中间件、负载均衡、网络组件及直接上下游。系统不存在或核心关系缺失时仍输出数据缺口报告，不得虚构拓扑。
2. 根据资产重要度和角色划定监控对象。关键生产 CI 必须检查告警和指标覆盖；外围依赖只在 CMDB 明确关联且与健康判断有关时深入调查。
3. 先调查告警总体分布和指标覆盖，再根据异常、阈值越界或趋势疑点查询必要明细。指标必须先确认实际存在，不能根据 CI 类型猜测名称。
4. 调查与关键 CI 相关的历史事件，识别反复故障、共同故障域、单点、依赖传播、性能退化和容量逼近。
5. 将所有运行事实映射回 CMDB 对象和关系，按 [inspection-rules.md](references/inspection-rules.md) 判断健康状态与评分，并按 [output-contract.md](references/output-contract.md) 输出。

## 工具选择规则

- 批量能力存在时优先按工具 Schema 的上限分批查询，避免逐个 CI 重复调用。
- 先使用汇总结果定位异常；只有在需要判断持续时间、趋势或瞬时峰值时才查询原始采样或告警明细。
- 工具成功但返回空结果时，记录查询对象和窗口；空结果不等于健康。
- 只对明确的瞬时错误重试一次；参数错误、权限拒绝和确定性空结果不得盲目重试。
- 相同工具、参数和时间窗口已有有效结果时不得重复调用。
- 达到完成条件或已确认剩余数据不可获得时停止调查，避免无效调用持续消耗 Token。
- Skill 只分析和建议，不执行重启、切换、扩容、封禁等生产操作。

## 必需证据

给出 `HEALTHY` 前必须覆盖以下证据域；无法取得时说明缺口及影响，不得以其他域的正常结果替代：

- 应用模块、运行实例和 IP 节点
- 数据库、中间件、负载均衡或网络组件
- 直接上下游及关键依赖关系
- 关键 CI 的告警覆盖与活动告警
- 关键 CI 的性能与容量指标覆盖
- 与当前系统相关的历史生产事件

## 证据约束

- 不得虚构 CI、IP、指标名、指标值、阈值、告警或事件。
- 每个风险必须包含 `evidenceRefs`，引用 `evidence` 中包含来源域、实际工具、对象和时间窗口的事实。
- 区分“当前故障”“容量隐患”“历史风险”和“监控缺失”。
- 单一瞬时峰值不得直接判定长期容量不足；应结合 P95、最近值、越界次数和趋势。
- 外部依赖只评估 CMDB 明确返回且有监控数据的对象；否则记录数据缺口。

## 输出要求

交互式使用时先给结论摘要，再给资产范围、异常发现、容量发现、拓扑风险、数据缺口和建议。被 API 提示要求 JSON 时，只输出 JSON 对象，不输出 Markdown 或代码围栏。只有资产、告警、性能容量和历史证据覆盖充分时才能判定 `HEALTHY`。
